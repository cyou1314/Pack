# CHAT-BRIEF：v1.1 房间闲聊（运行时聊天回路）

## 背景与目标
v1.0 的房间只有任务卡能触发成员，群主发普通消息无人接话（2026-11-19 22:20 群主实测「有谁在回个话」石沉大海）。群主拍板：v1.1 第一件做房间闲聊。本简报只做 **absent 经 ego 运行时的聊天回路**；调度员在场由调度员在 VM 侧另行实现，不归本片。

先读：ROOM-SESSION-DESIGN.md（房间=一条连续对话、回水集）、runtime/ 现行代码与 runtime/tests/。

## 触发规则（与转卡严格不冲突）
运行时新增聊天回路，轮询 pack-main 房间消息（absent 令牌），本地状态文件持久化 last_chat_id 水位。只处理 kind=chat 的消息，且满足其一：
1. **群主（owner）的普通消息**：正文不含对任何成员的 @ 提及（用与 watcher 相同的提及匹配口径判定；含 @ 的归 watcher 转卡，本回路跳过）；
2. **调度员（dispatcher）的接话召唤**：author=dispatcher 且正文含 @absent。
跳过：自己发的、task_card / decision / approval_request、已处理过的 id。串行处理，一次一条。

## 对话连续性
- 每个房间在 absent 的网页会话里维护**一条**连续对话：首次使用时新建对话并发送种子说明（一条消息讲清：你是 absent、这是 ♾️ 群聊房间 pack-main、群主的话会原样转进来、你以 absent 身份简短自然地回话、不接任务语义、单条回复控制在 200 字内），把对话标识（URL）持久化到运行时本地状态。
- 后续把触发消息正文原样送进该对话，取回复，以 absent 身份 room_post 回房间（kind=chat）。
- 网页会话失效/报错：不发任何东西、记日志、退避后重试下一轮；连续失败 3 次停一轮长退避，不要刷屏报错进房间。

## 额度帽
- 每轮处理前读中枢 absent 额度：周已用 ≥90% 时跳过闲聊（只记日志，不回房间），任务路不受影响。
- 闲聊回复不走任务信封、不建卡、不写 runs。

## 施工与验收
- 改动只限 runtime/（含 tests）；不动 hub.py、不动桥、不动 App。
- 新增纯函数分类测试（触发判定：owner 普通消息 / owner @ 消息跳过 / dispatcher 召唤 / 自身与系统 kind 跳过 / 水位去重），node --check + 现有测试全过。
- 部署：同步到 Mac ~/pack-runtime/ 并重启 launchd 运行时，确认心跳恢复、任务路不回归（认领口径不变）。
- 实测验收（部署后做，记进结果文件）：调度员在房间以 owner 口径外的方式无法代发 owner 消息——实测须等群主真发一条普通消息；部署完成后先在结果文件写明「待群主实测」，并在线程报告。不要用 API 冒充 owner 发言做假验收。
- 结果写回仓库 `CHAT-RESULT.md` 并提交推仓；线程发简版报告。

## 红线
- 不改中枢行为与 watcher 规则；@ 转卡语义一字不动。
- 不碰账号密码/验证码；网页要求重登时停下记录。
- 不动生产 App、引擎、桥进程。
